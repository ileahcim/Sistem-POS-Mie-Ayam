## Zona waktu

Warung berlokasi di Indonesia (WIB, UTC+7, tidak ada daylight saving). **Setiap kode server yang mengelompokkan per hari, menghitung rentang tanggal, menentukan batas awal/akhir hari, atau menampilkan tanggal/jam ke pengguna WAJIB lewat `src/lib/timezone.ts`** (`localDateStr`, `localTimeStr`, `localDateParts`, `mondayOfLocalWeek`, `formatId`) — jangan pernah `date.getHours()`/`getFullYear()`/dst secara langsung, jangan pernah `date.toISOString().slice(...)`, dan jangan pernah `new Intl.DateTimeFormat(...)` tanpa `timeZone` eksplisit.

**Kenapa ini bukan cuma soal gaya kode:** `getHours()` dkk dan `Intl.DateTimeFormat` tanpa `timeZone` eksplisit itu benar HANYA karena kebetulan OS jam server-nya sudah Asia/Jakarta. Begitu di-deploy ke Vercel (Tahap 12), serverless function-nya jalan di UTC — kode yang sama, tanpa berubah sebaris pun, diam-diam menggeser semua jam yang ditampilkan mundur 7 jam (shift tutup jam 20:00 WIB akan tertampil "13:00"), dan transaksi jam 00:00-06:59 WIB bisa masuk hitungan omzet hari SEBELUMNYA (karena jam segitu masih hari sebelumnya kalau dibaca sebagai UTC). `src/lib/timezone.ts` selalu benar di lingkungan apa pun karena memaksa `timeZone: "Asia/Jakarta"` eksplisit ke Intl API, tidak pernah bergantung ke default runtime — sudah dibuktikan dengan menjalankan logikanya di bawah `TZ=UTC` dan `TZ=Asia/Jakarta` sekaligus, hasilnya identik persis.

Yang **tidak** perlu lewat helper ini (aman secara desain, bukan kebetulan):
- Window rolling N-hari (`Date.now() - N*24*60*60*1000`, dipakai combo cache Tahap 10 & dashboard Tahap 11) — ini pengurangan durasi murni terhadap instant absolut, bukan operasi batas kalender, jadi timezone tidak relevan sama sekali di sini.
- Perbandingan instant-vs-instant (`scheduledFor > now`, dst) — sama, tidak ada aritmetika kalender.
- Penulisan timestamp mentah (`paidAt: new Date()`, `voidedAt: new Date()`, dst) — kolom `timestamptz` menyimpan instant absolut, selalu benar tanpa ambiguitas; zona waktu cuma relevan saat instant itu nanti DITAMPILKAN atau DIKELOMPOKKAN per hari.
- Input tanggal/jam dari kasir di layar (`preorder-screen.tsx`'s `new Date(\`${date}T${time}\`)`) — ini jam dinding perangkat tablet itu sendiri, bukan kode server; asumsinya OS tablet memang di-set ke WIB (sama seperti asumsi struk tercetak butuh printer nyala), bukan sesuatu yang bisa "dipusatkan" lewat kode.

Diaudit ulang Tahap 12: satu-satunya bug nyata yang ketemu adalah nama file export Excel (`toISOString().slice()`, sudah diperbaiki) — semua pengelompokan kalender lain (grafik omzet, window 30 hari menu populer/dashboard) sudah lolos audit atau sudah dipindah ke helper terpusat ini.

## Rendering dinamis — JANGAN dihapus dari root layout

`src/app/layout.tsx` punya `export const dynamic = "force-dynamic"`. **Ini bukan boilerplate, jangan pernah dihapus atau di-override `"auto"`/`"force-static"` di layout/page mana pun** — ditemukan waktu persiapan deploy Tahap 12 lewat `next build` + `next start` beneran (bukan cuma `next dev`), bukan dari membaca dokumentasi saja.

**Masalahnya:** halaman yang HANYA memanggil Prisma (tanpa `cookies()`/`headers()` sendiri — misalnya `kasir/page.tsx` yang cuma manggil `getOpenShift()`/`getActiveMenu()`, autentikasinya sendiri ditangani `src/proxy.ts`, bukan di page-nya) tidak memberi sinyal apa pun ke static-analysis Next.js bahwa halaman itu perlu dirender ulang tiap request — Prisma bukan `fetch()`, jadi tidak kelihatan oleh heuristik caching Next.js. Akibatnya beberapa halaman (Kasir, Piutang, Pesanan Terjadwal, Buka Shift, Input Pengeluaran) otomatis ditandai statis oleh `next build` ("○ Static") dan di-render SEKALI lalu HTML-nya dibekukan selamanya — dibuktikan langsung: harga produk diubah paksa lewat DB saat `next start` jalan, reload keras di browser tetap menampilkan harga lama, sampai `dynamic = "force-dynamic"` ditambahkan di root layout (yang otomatis berlaku ke semua route di bawahnya) dan build ulang — baru setelah itu semua 21 halaman aplikasi tertandai "ƒ Dynamic" dan harga baru langsung muncul di request berikutnya.

Tidak ada halaman yang benar-benar statis di aplikasi ini (semua butuh data live atau sesi live), jadi memaksa dinamis di root layout adalah default yang benar untuk SELURUH pohon route, bukan sesuatu yang perlu di-opt-in per halaman baru. Kalau suatu saat ada halaman yang benar-benar ingin di-cache (jarang, dan harus didiskusikan dulu), override `dynamic` di halaman ITU secara eksplisit — jangan mengubah default root layout.

## Auth

- Login pakai **username + password**, tidak ada konsep email yang terlihat user. Di balik layar dipetakan ke email sintetis (`username@warung.local`) untuk Supabase Auth. Verifikasi email harus OFF di project Supabase (domain sintetis tidak bisa terima email).
- Rencana masa depan (belum dibangun): layar kasir auto-login permanen (device-level session, tidak pernah lihat halaman login); dashboard OWNER dikunci password dengan session timeout idle yang balik ke layar kasir; identitas kasir individual dipakai lewat PIN 4 digit saat buka shift, bukan username/password.

## Server-side authorization

Setiap aksi khusus role OWNER **wajib** memanggil `requireRole("OWNER")` (dari `src/lib/auth/get-current-user.ts`) sebagai baris pertama di server action-nya sendiri — bukan cuma menyembunyikan tombol di UI. Menyembunyikan tombol itu UX, bukan keamanan; siapa pun bisa memicu server action lewat devtools tanpa lewat tombol sama sekali.

Sudah diverifikasi (bukan cuma dibaca kodenya): request asli ditangkap dari sesi OWNER yang klik "Batalkan", lalu direplay langsung ke server dari sesi CASHIER sungguhan (login beneran, request sungguhan, order id berbeda) — server menolak dengan HTTP 500 `"Forbidden: requires role OWNER"`, dan data di database tidak pernah berubah. Pola ini (`requireRole` di baris pertama action) wajib dipakai persis sama untuk setiap fitur OWNER-only berikutnya (dashboard, ubah harga, manajemen menu, manajemen user) begitu dibangun — dan diverifikasi dengan cara yang sama (capture request asli dari sesi berwenang, replay dari sesi tidak berwenang, cek server menolak DAN data tidak berubah), bukan cuma dicek lewat UI.

Diverifikasi ulang 20 Sep 2026 (build produksi lokal, sesi `owner` dan `kasir` sungguhan) untuk `updatePrinterDriver`, `updatePrintLogo`, dan `updatePrintTuning`: kontrol positif dari sesi OWNER (nilai = kondisi sekarang → `{"ok":true}`, membuktikan format request benar), lalu replay dari sesi CASHIER dengan nilai BERBEDA → HTTP 500, dan baris `Setting` identik sebelum/sesudah; nilai di luar rentang dari OWNER ditolak validasi server dengan pesan jelas. Halaman `/print-preview` juga OWNER only: kasir yang membukanya dialihkan ke `/kasir`.

Diverifikasi 21 Sep 2026 dengan cara yang sama untuk `updatePreorderReminderMinutes`: kontrol positif dari sesi OWNER (pilih "3 jam" → kolom benar-benar jadi 180 di DB, jadi format request-nya terbukti benar), lalu request itu di-replay dari sesi `kasir` sungguhan dengan nilai BERBEDA tapi tetap sah (360) → HTTP 500, dan `preorderReminderMinutes` tetap 180 sebelum/sesudah.

Diverifikasi 21 Sep 2026 untuk `cancelOrderWithDeposit` (aksi OWNER baru, `requireRole("OWNER")` di baris pertama): request asli ditangkap dari sesi OWNER yang menekan "Ya, Batalkan — DP Hangus" (kontrol positif: order jadi `CANCELLED` dan ledger mencatat `FORFEITED`), lalu di-replay dari sesi `kasir` sungguhan ke order LAIN yang juga ber-DP dan dengan pilihan berbeda (`REFUND`) → HTTP 500, order itu tetap `OPEN` dan ledger DP-nya tidak berubah. Aksi DP lain (`recordDeposit`, `getDepositReceipt`) memang boleh CASHIER (uang masuk, sama seperti membayar), jadi tidak OWNER-only.

## Design System

Semua layar wajib pakai token dan komponen terpusat ini — tidak ada lagi warna/radius/spacing pilihan sendiri per halaman.

**Token** (`src/app/globals.css`, via `@theme`): warna (`bg-canvas`, `bg-surface`, `text-ink` / `text-ink-muted` / `text-ink-faint`, `bg-primary` / `bg-primary-soft`, `bg-muted`, `bg-danger` / `bg-warning` / `bg-info` + varian `-soft`; bingkai foto produk: `border-photo-frame` dan `bg-photo-canvas`), radius (`rounded-pill`, `rounded-card`, `rounded-sheet`, `rounded-input`), shadow (`shadow-card`, `shadow-sheet`). Warna hijau (`--color-primary`) didekati dari referensi GoFood — bukan pixel-perfect (sumbernya foto WhatsApp), tapi searah.

**Tidak ada dark mode otomatis.** Ini kios di tablet tetap, bukan situs konsumen — tablet yang tiba-tiba ganti ke palet gelap yang belum pernah diuji di tengah shift lebih buruk daripada tidak pernah mendukung dark mode sama sekali.

**Komponen bersama** (`src/components/ui/`): `Button` (primary/secondary/ghost/danger — client, pakai `motion` untuk scale saat ditekan), `LinkButton` (tampilan identik `Button` tapi untuk navigasi `<Link>`, server-renderable, TIDAK boleh impor apa pun dari `button.tsx` karena itu file `"use client"` — style bersama ada di `button-styles.ts` yang netral), `Card` (permukaan putih di atas `bg-canvas`), `ListRow` (baris list dengan padding konsisten; pakai `onClick` untuk aksi in-page atau `asLink` untuk navigasi), `Sheet` (shell bottom sheet dengan drag handle), `Badge`, `PriceText` (lihat aturan hierarki di bawah).

**Aturan hierarki harga** (perbaikan dari `PriceText` weight prop) — dulu nama item dan harga sama-sama bold, sekarang:
- `weight="primary"`: harga produk sendiri di halaman custom/detail (subjek utama baris itu).
- `weight="secondary"`: harga di baris keranjang/order-item (nama item yang bold/subjek, harga jadi angka pendukung di sebelahnya), dan harga opsi add-on.
- `weight="total"`: SATU angka yang paling penting di layar itu (Total, Subtotal-sebagai-penutup-list, Selisih kas) — lebih besar, bold, dipisah garis pembatas dari baris-baris di atasnya. Subtotal/Total tidak boleh terlihat seperti baris item biasa.

**Satu aksi utama per layar/kartu.** Kalau ada dua tombol berdampingan, cuma satu yang `variant="primary"` (hijau solid, dominan) — sisanya `secondary`/`ghost`. Jangan biarkan dua tombol sama menonjolnya berebut perhatian.

**Animasi** (pakai `motion`, tidak ada properti yang memicu layout reflow, supaya ringan di tablet Android entry-level):
- **Sheet add-on Kasir ("Custom pembelian") sengaja TANPA animasi sama sekali** (`<Sheet animated={false}>`, tidak memakai `SheetItem`) — satu-satunya sheet yang begitu. Alasannya bukan selera: pembungkus stagger menyusutkan seluruh baris ke `scale 0.95` saat ditekan, dan di layar lebar itu menggeser tombol `+` selebar 48px sekitar 30px dari bawah kursor antara mousedown dan mouseup, jadi browser mengirim `click` ke barisnya, bukan ke tombolnya — stepper add-on tidak bisa dinaikkan sama sekali di laptop/tablet lebar (terbukti dan diperbaiki dengan tes klik di 1366px, 1180px, 390px, dan 844×390). Sheet ini dibuka puluhan kali per shift dan isinya banyak target kecil, jadi kecepatan dan ketepatan sentuh menang atas estetika. **Jangan kembalikan animasinya.** Sheet lain (Menu, popup konfirmasi, Pisahkan & Bayar, sheet Note) tetap beranimasi.
- **Sheet & popup lain** (permintaan pemilik — `Sheet`: Menu, popup konfirmasi Batalkan/Void, Pisahkan & Bayar, sheet Note): kontainer muncul dengan spring ~0.4s dari `y:-5, scale:0.95, blur(10px), opacity:0`; item di dalamnya muncul berurutan (`delay: index × 0.05`, dari `x:10, scale:0.95, blur`); item yang bisa di-tap punya hover (tint background, 0.4s) dan tap (scale 0.95, 0.2s). Semua di `src/components/ui/sheet-motion.tsx` (`sheetPanelMotion`, `SheetItem`, `HoverTint`) — pakai itu, jangan bikin variasi sendiri. **Pelajaran dari sheet add-on di atas: jangan pernah menaruh tombol kecil (stepper, ikon) di dalam `SheetItem interactive`** — pembungkus yang menyusut memindahkan tombolnya dari bawah kursor. Aman kalau seluruh baris itu sendiri yang jadi targetnya (Menu, daftar konfirmasi).
  - **Blur itu mahal di GPU** (pemilik sadar dan tetap mau): ada toggle **"Efek blur animasi"** di `/admin/settings` (`Setting.sheetBlurEnabled`, dibaca root layout tiap request lewat `getSheetBlurEnabled` → `SheetMotionProvider`) — kalau tersendat di tablet asli, pemilik mematikannya sendiri; gerak spring/stagger tetap ada, cuma blur yang hilang.
  - **`prefers-reduced-motion`**: tanpa blur dan tanpa gerak sama sekali, cuma fade 0.15s.
- Tekan tombol: scale ke 0.97-0.99, ~120ms (built-in di `Button`/`ListRow`/`ProductButton`).
- Item baru masuk keranjang: fade+scale singkat (~200ms), item lain di keranjang tidak ikut animasi.
- **Instan, tanpa animasi apa pun:** ganti kategori, tap tombol produk (aksinya, bukan feedback tekan), navigasi antar halaman.

**Header aplikasi — satu komponen untuk semua layar** (`AppHeader`, `src/components/ui/app-header.tsx`): tombol **Menu di kiri atas** (isi menu sama persis di mana pun — `MainMenu`, termasuk Kasir dan Order Aktif supaya dari Dashboard bisa langsung ke Note dll.), judul, aksi khusus halaman (Kembali/Batal pakai `size="compact"`, tetap 48px), lalu tombol Order Aktif paling kanan — satu bidang putih dengan satu garis bawah. Data header dari `getHeaderNav()` (indikator Order Aktif + `isOwner` untuk menyembunyikan entri OWNER — itu UX, bukan pengaman). Di HP label "Menu" disembunyikan (ikon saja) dan judul boleh 2 baris; judul yang tetap terlalu panjang di 390px dipendekkan (mis. "Harga Mi Mentah"). **Kasir** menyusun header sendiri dari potongan yang sama: tablet (≥1024px) satu baris Menu · channel/meja · Order Aktif; lebih sempit jadi dua baris terpisah (Menu + "Kasir" + Order Aktif, lalu baris channel selebar layar) supaya tombol channel tidak pernah tertimpa. **Pengecualian: jendela pendek (`max-height:500px`, yaitu HP landscape 844×390) balik ke satu baris** — di sana ruang vertikal yang langka, bukan lebar, jadi dua baris header malah memakan tab kategori. Halaman baru yang punya header wajib memakai `AppHeader`.

**Kasir — kategori & kartu produk:**
- Tab kategori **netral**: semua abu-abu muda (`bg-muted`) teks gelap, **hanya yang aktif hijau brand**; ikon kecil ikut warna teks. Tidak ada lagi warna per kategori (token `--color-cat-*` sudah dihapus).
- **Kartu produk bergambar**: gambar 4:3 di atas, nama, harga paling bawah; grid 2 kolom di HP, 3 kolom mulai ≥768px (dipakai juga oleh Pre-order dan Tambah Item — komponen yang sama). **Tinggi area gambar dibatasi `max-h-[140px]`** (dan 84px di jendela pendek, `max-height:500px` — HP landscape), karena rasio 4:3 tanpa batas atas bikin satu foto makan setengah layar di tablet 1366px. Lebarnya mengikuti kartu. Dengan batas ini 1180×820 dan 1366×1024 sama-sama muat 2 baris produk penuh.
  - **Foto dimuat UTUH (`object-contain`) di atas kanvas putih dengan bingkai 1px** (permintaan pemilik, 21 Sep 2026). Foto produk berlatar putih, jadi tanpa bingkai batasnya menyatu dengan kartu putih; dan `object-cover` memotong botol yang tinggi. Bingkai = token `--color-photo-frame` (abu-abu transparan, tipis), kanvas = token `--color-photo-canvas`. **Kalau suatu hari ada dark mode: definisikan ulang `--color-photo-frame` lebih terang, tapi biarkan `--color-photo-canvas` PUTIH** — file fotonya berlatar putih, kanvas gelap akan memunculkan batang putih di kiri-kanan foto.
  - **Kotak foto MASUK 6px dari tepi kartu, tidak menempel**, dengan sudut konsentris (radius kartu − 1px border − 6px inset = 9px, ditulis `rounded-[calc(var(--radius-card)-7px)]` di `product-button.tsx` — ubah bersama kalau inset/border kartu berubah). Menempel di tepi berarti bingkainya jatuh di atas garis tepi kartu dan terlihat sebagai satu garis tebal. Placeholder memakai inset dan sudut yang sama tapi TANPA bingkai (warnanya sendiri sudah menandai batas), supaya nama produk sebaris tetap sejajar. `ProductImage` juga dipakai thumbnail di Foto Produk, jadi ikut berbingkai.
  - Terukur 21 Sep 2026 (sebelum → sesudah): kapasitas grid Kasir 1366×1024 4,16 → 4,05 baris, 390×844 2,70 → 2,74, 844×390 1,11 → 1,07 (tinggi kartu +6px di tablet dan HP landscape, −3px di HP portrait karena lebar kotak foto menyempit). Layar Pre-order Baru di 844×390 sudah sempit dari dulu (baris tanggal + channel + tab memakan 252 dari 390px) — bukan akibat bingkai.
- Tanpa foto → **placeholder** (`ProductImage`, `src/components/ui/product-image.tsx`): blok warna lembut + inisial nama, warna diturunkan dari hash nama (sama di setiap render/perangkat). **Jangan pernah** memakai foto dari Google/stok — pemilik mengunggah fotonya sendiri.
- **Foto Produk** (`/admin/foto-produk`, OWNER, dijangkau dari halaman Pengaturan — bersama "Isi HPP"; dua-duanya diisi sekali lalu jarang disentuh, jadi sengaja TIDAK di Menu utama): unggah/ganti/hapus per produk. Browser memuat foto UTUH ke kanvas putih 800×600 (rasio 4:3, **tidak dipotong**; `resizeToCard`, `src/lib/images/resize-to-card.ts`) dan mengecilkannya ke WebP (~60-120 KB) sebelum kirim — PNG transparan ikut diratakan di atas putih. **Dulu foto dipotong-tengah ke 4:3 saat unggah dan hasil potongannya yang disimpan**: botol tinggi (1:3) tinggal ±25% bagian tengah, tutup dan dasarnya hilang selamanya, dan `object-fit` di kartu tidak bisa mengembalikannya. Diperbaiki 21 Sep 2026, sebelum ada satu pun foto terunggah (0 dari 25 produk) — jadi tidak ada foto lama yang perlu diunggah ulang; kalau suatu hari ada, foto yang diunggah sebelum tanggal itu tetap terpotong. Fungsinya diuji langsung di Chromium (21 pemeriksaan piksel: botol tinggi utuh, 4:3 identik dengan algoritma lama, lebar/kotak, PNG transparan). Action `uploadProductImage`/`removeProductImage` (`requireRole("OWNER")` baris pertama, diverifikasi replay dari sesi CASHIER — ditolak, data dan storage tidak berubah) menyimpan ke bucket Supabase Storage **`product-images`** (publik baca; tulis hanya OWNER lewat RLS `public.is_pos_owner()` — sesi kasir yang upload langsung ke bucket juga ditolak). Bucket + policy dibuat oleh migrasi `20260918090000_product_images_bucket`, jadi database production nanti ikut punya. Nama file baru tiap upload (URL berubah → tablet tidak menampilkan foto lama dari cache), file lama dihapus.

**Jebakan client/server yang sudah dua kali kejadian** — kalau bikin komponen UI baru yang punya varian client (butuh interaktivitas/motion) dan varian server-renderable (misal cuma `<Link>`), taruh logic/class yang dipakai bersama di file netral TANPA `"use client"`, jangan saling impor fungsi antar file client dan server. Lihat `button-styles.ts` sebagai contoh polanya.

**File `"use server"` CUMA boleh mengekspor fungsi async** — dan melanggarnya **lolos dari `next build`**. Kejadian 20 Sep 2026: `PREORDER_REMINDER_CHOICES` (sebuah array) diekspor dari `src/app/admin/settings/actions.ts`; `tsc`, `eslint`, dan `npm run build` semuanya bersih, tapi di runtime seluruh modul action itu gagal dimuat dengan `A "use server" file can only export async functions, found object` — dan kartu Pengaturan tetap menampilkan "Tersimpan ✓" padahal tidak ada yang tersimpan ke database. Taruh konstanta bersama di file netral (`src/lib/settings/preorder-reminder.ts`). **Pelajaran yang lebih besar: build yang hijau bukan bukti aksi server benar-benar jalan — cek nilainya di DB setelah menekan tombolnya.**
