## Zona waktu

Warung berlokasi di Indonesia (WIB, UTC+7, tidak ada daylight saving). **Setiap kode server yang mengelompokkan per hari, menghitung rentang tanggal, menentukan batas awal/akhir hari, atau menampilkan tanggal/jam ke pengguna WAJIB lewat `src/lib/timezone.ts`** (`localDateStr`, `localTimeStr`, `localDateParts`, `mondayOfLocalWeek`, `formatId`) — jangan pernah `date.getHours()`/`getFullYear()`/dst secara langsung, jangan pernah `date.toISOString().slice(...)`, dan jangan pernah `new Intl.DateTimeFormat(...)` tanpa `timeZone` eksplisit.

**Kenapa ini bukan cuma soal gaya kode:** `getHours()` dkk dan `Intl.DateTimeFormat` tanpa `timeZone` eksplisit itu benar HANYA karena kebetulan OS jam server-nya sudah Asia/Jakarta. Begitu di-deploy ke Vercel (Tahap 12), serverless function-nya jalan di UTC — kode yang sama, tanpa berubah sebaris pun, diam-diam menggeser semua jam yang ditampilkan mundur 7 jam (shift tutup jam 20:00 WIB akan tertampil "13:00"), dan transaksi jam 00:00-06:59 WIB bisa masuk hitungan omzet hari SEBELUMNYA (karena jam segitu masih hari sebelumnya kalau dibaca sebagai UTC). `src/lib/timezone.ts` selalu benar di lingkungan apa pun karena memaksa `timeZone: "Asia/Jakarta"` eksplisit ke Intl API, tidak pernah bergantung ke default runtime — sudah dibuktikan dengan menjalankan logikanya di bawah `TZ=UTC` dan `TZ=Asia/Jakarta` sekaligus, hasilnya identik persis.

Yang **tidak** perlu lewat helper ini (aman secara desain, bukan kebetulan):
- Window rolling N-hari (`Date.now() - N*24*60*60*1000`, dipakai combo cache Tahap 10 & dashboard Tahap 11) — ini pengurangan durasi murni terhadap instant absolut, bukan operasi batas kalender, jadi timezone tidak relevan sama sekali di sini.
- Perbandingan instant-vs-instant (`scheduledFor > now`, dst) — sama, tidak ada aritmetika kalender.
- Penulisan timestamp mentah (`paidAt: new Date()`, `voidedAt: new Date()`, dst) — kolom `timestamptz` menyimpan instant absolut, selalu benar tanpa ambiguitas; zona waktu cuma relevan saat instant itu nanti DITAMPILKAN atau DIKELOMPOKKAN per hari.
- Input tanggal/jam dari kasir di layar (`preorder-screen.tsx`'s `new Date(\`${date}T${time}\`)`) — ini jam dinding perangkat tablet itu sendiri, bukan kode server; asumsinya OS tablet memang di-set ke WIB (sama seperti asumsi struk tercetak butuh printer nyala), bukan sesuatu yang bisa "dipusatkan" lewat kode.

Diaudit ulang Tahap 12: satu-satunya bug nyata yang ketemu adalah nama file export Excel (`toISOString().slice()`, sudah diperbaiki) — semua pengelompokan kalender lain (grafik omzet, window 30 hari menu populer/dashboard) sudah lolos audit atau sudah dipindah ke helper terpusat ini.

## Rendering dinamis — JANGAN dihapus dari root layout

`src/app/layout.tsx` punya `export const dynamic = "force-dynamic"`. **Ini bukan boilerplate, jangan pernah dihapus atau di-override `"auto"`/`"force-static"` di layout/page mana pun** — ditemukan waktu persiapan deploy Tahap 12 lewat `next build` + `next start` beneran (bukan cuma `next dev`), bukan dari membaca dokumentasi saja.

**Masalahnya:** halaman yang HANYA memanggil Prisma (tanpa `cookies()`/`headers()` sendiri — misalnya `kasir/page.tsx` yang cuma manggil `getOpenShift()`/`getActiveMenu()`, autentikasinya sendiri ditangani `src/proxy.ts`, bukan di page-nya) tidak memberi sinyal apa pun ke static-analysis Next.js bahwa halaman itu perlu dirender ulang tiap request — Prisma bukan `fetch()`, jadi tidak kelihatan oleh heuristik caching Next.js. Akibatnya beberapa halaman (Kasir, Piutang, Pesanan Terjadwal, Buka Shift, Input Pengeluaran) otomatis ditandai statis oleh `next build` ("○ Static") dan di-render SEKALI lalu HTML-nya dibekukan selamanya — dibuktikan langsung: harga produk diubah paksa lewat DB saat `next start` jalan, reload keras di browser tetap menampilkan harga lama, sampai `dynamic = "force-dynamic"` ditambahkan di root layout (yang otomatis berlaku ke semua route di bawahnya) dan build ulang — baru setelah itu semua 21 halaman aplikasi tertandai "ƒ Dynamic" dan harga baru langsung muncul di request berikutnya.

Tidak ada halaman yang benar-benar statis di aplikasi ini (semua butuh data live atau sesi live), jadi memaksa dinamis di root layout adalah default yang benar untuk SELURUH pohon route, bukan sesuatu yang perlu di-opt-in per halaman baru. Kalau suatu saat ada halaman yang benar-benar ingin di-cache (jarang, dan harus didiskusikan dulu), override `dynamic` di halaman ITU secara eksplisit — jangan mengubah default root layout.

Ukuran sentuh tombol **tidak pernah dikecilkan** (tetap ≥48px) — yang dipangkas cuma padding/gap/tinggi baris di sekitarnya. `ListRow` (`src/components/ui/list-row.tsx`) punya prop `dense` khusus untuk ini — dipakai HANYA di Order Aktif (`order-row.tsx`, unpaid-served list di `order-aktif-list.tsx`). Jangan pakai `dense` di layar lain (Piutang, Pesanan Terjadwal, Dashboard, laporan, Tutup Shift) — layar-layar itu dipakai duduk dan sengaja tetap lega.

Order yang di-void tidak dihitung sebagai penjualan cash saat rekonsiliasi shift (`closeShift` cuma menjumlah `PAID`), jadi kalau shift-nya masih terbuka, uangnya harus dikembalikan dari laci. ## Split payment ("Pisahkan & Bayar") — sudah dibangun

Kasus rombongan yang duduk di satu meja tapi mau bayar terpisah:
- **Tidak** ada fitur gabung order / pindah meja.
- Ada tombol **"Pisahkan & Bayar"** di halaman order: kasir centang sebagian item → sistem memindahkan item tercentang ke **order baru** dengan nomor antrian = nomor asli + suffix huruf (contoh: order #18 dipisah jadi `18-A`) → order baru itu langsung masuk alur pembayaran.
- Order induk tetap terbuka dengan sisa item yang tidak dipindah.
- Aturan keras: **satu order = satu pembayaran = satu struk**. Jangan pernah membuat order yang bisa dibayar berkali-kali.
- Ini kasus jarang — jangan sampai menambah langkah di alur pembayaran normal (single order, bayar sekali) untuk mengakomodasi ini.
- **Tampilan: dua panel berdampingan** (di layar sempit bertumpuk, panel kanan di bawah): kiri "Tetap di order ini", kanan "Dipisah & dibayar sekarang" (kosong di awal: "Belum ada item dipilih"), masing-masing dengan subtotal sendiri. Tap kartu di kiri = pindahkan 1 porsi ke kanan, tap kartu di kanan = kembalikan 1 porsi; kartu hilang dari panel begitu qty-nya 0. **Tanpa teks instruksi** — bentuk dua panel sudah cukup jelas. Animasi perpindahan cuma transform+opacity, singkat. Tombol "Pisahkan & Lanjut Bayar" aktif kalau panel kanan terisi (dan panel kiri masih menyisakan minimal 1 item — server menolak memindah semuanya; untuk itu pakai alur bayar biasa). Ini menggantikan versi lama (satu daftar dengan stepper − 0 +) yang terlalu ribet dipakai cepat.

## Ongkir (channel Antar)

- Rp1.000 per porsi kategori **Makanan saja** (bukan Minuman Racik/Kulkas/Lain-lain/Frozen), dihitung per qty bukan per baris.
- Baris terpisah di struk setelah subtotal.
- Tidak ada minimum ongkir — penolakan order kecil diputuskan manual oleh owner, bukan sistem.

## Struk & printer

- Print **hanya sekali**, saat pembayaran (otomatis kalau `Setting.autoPrintReceipt` nyala; kalau mati, kasir ditanya "Cetak struk?"). Cetak ulang dari Riwayat Pesanan tetap ada. Sudah tercetak di kertas asli lewat Web Bluetooth (19-20 Sep 2026).
- Item dengan nama + add-on identik digabung jadi satu baris dengan qty, lalu diurutkan dengan aturan yang sama dengan layar (kategori → produk → termurah dulu; lihat "Urutan baris" di "Order & status"). Sejak 21 Sep 2026 urutan item di kertas BERUBAH untuk semua order, termasuk cetak ulang order lama — itu disengaja.
- Khusus channel Antar: tombol **"Print Daftar"** terpisah, dipakai **sebelum** bayar — judul "DAFTAR PACKING", kotak centang kosong di kiri tiap nama menu (`[ ]` di kertas, `□` di layar), qty dicetak tebal, **tanpa harga/total** (ini daftar packing, bukan bukti bayar). Dibangun Tahap 8.
- Nama warung, alamat, telepon, footer struk **selalu** dari tabel `Setting` (singleton), tidak pernah di-hardcode di kode. **Tidak ada satu pun teks tetap di header** — di bawah logo langsung nama warung dari `Setting` (caption "CIPTA RASA GROUP" dihapus 20 Sep 2026: mengulang identitas yang sudah tercetak di baris berikutnya).

**Isi struk ditentukan di SATU tempat — jangan ditulis dua kali lagi.**
- `src/lib/printing/receipt-layout.ts` (`buildReceiptLayout`, `buildPackingListLayout`) menghasilkan daftar baris: urutan, semua label (`CHANNEL_LABEL`, `PAYMENT_LABEL`), format tanggal/jam (lewat `timezone.ts`), pasangan nama-harga, garis pemisah, penutup. Dua renderer hanya membacanya: `components/printing/paper-view.tsx` (HTML — preview MockPrinter lewat `ReceiptView`/`PackingListView`) dan `escpos.ts` (byte ESC/POS untuk printer). Mereka boleh beda **hanya cara menggambar**: CSS `font-bold` vs perintah `ESC E`, `□` vs `[ ]`. Penekanan ada di `styledText`/`totalRow`/`boldTailRow` di `escpos.ts` dan di kelas `font-bold` yang sepadan di `paper-view.tsx` (Total tebal seluruh baris; daftar packing cuma qty-nya). **Jangan menyalin label/format ke renderer, jangan bikin layout kedua.** Sebelum modul ini, layar dan kertas sudah menyimpang (kertas: garis raster, "Tel:", tanpa judul packing; layar: sebaliknya).
- **MockPrinter (`ReceiptView`) adalah acuan isi dan struktur** (keputusan pemilik, 20 Sep 2026). Paritas diverifikasi dengan merender HTML dan byte dari data yang sama lalu membandingkan aliran teksnya (struk Antar dengan ongkir/catatan/add-on qty/item digabung, daftar packing, struk tanpa logo — identik).
- **Dua cetakan DP, keduanya dari `receipt-layout.ts` (satu sumber, seperti struk biasa):** (1) **"BUKTI UANG MUKA"** (`buildDepositReceiptLayout`, `printDepositReceipt` di tiap driver) — dicetak saat DP diterima, untuk dipegang pelanggan: warung, No. Order, Pemesan (nama panjang melanjut ke baris bawah, rata di bawah nilainya), tanggal/jam DP, Kasir, Tipe, **Kirim** (jadwal), daftar pesanan, Total, satu baris `DP <tgl>, <metode>` per DP (plus "Total DP" kalau lebih dari satu), dan **"Sisa dibayar saat diambil"** tebal. DP kedua mencetak bukti sendiri yang memuat SEMUA DP sampai saat itu. Tanpa nomor antrian dan tanpa baris bayar (pre-order belum punya antrian sebelum dibayar). (2) **Struk lunas** — kalau order punya DP, blok di bawah Total berganti jadi baris `DP <tgl>, <metode>` + **"Sisa dibayar (<metode>)"** (atau **"Kembalikan"** kalau order mengecil di bawah DP, **"Sisa dibayar Rp0"** kalau DP menutup semuanya) — baris `Bayar (...)` lama yang akan menyesatkan tidak dicetak. **Order tanpa DP tidak berubah satu byte pun**: 90 varian layout dan 180 aliran byte ESC/POS (dengan/tanpa logo) diuji identik dengan versi sebelum fitur ini, dan struk 23 order PAID nyata di DB juga identik. Paritas MockPrinter (HTML) vs kertas (byte) untuk kelima bentuk cetak DP diverifikasi sama seperti struk biasa (teks identik, tidak ada baris > 48 kolom).
- **Penekanan = TEBAL SAJA (`ESC E`), tidak pernah ukuran ganda.** Terukur di printer asli (Tes Ketajaman, 20 Sep 2026): huruf normal dan tebal tajam, tapi SETIAP varian 2x tinggi / 2x lebar meleber dan keseret — termasuk kombinasi yang dulu dipakai nama warung (2x tinggi + tebal) dan Total (2x lebar + tebal). Sekarang nama warung, judul "DAFTAR PACKING", Total, dan qty daftar packing semuanya tebal di ukuran normal, dan preview layar dibuat sama (tanpa `text-sm`/`text-base`/`text-lg`). **Jangan kembalikan bit ukuran `ESC !` tanpa tes ulang di kertas.**
- **Ketajaman cetak TIDAK bisa diatur — printer ini mengabaikannya.** Tes Ketajaman 20 Sep 2026 mencetak sembilan kombinasi `ESC 7` (titik/waktu/jeda pemanasan) dan `DC2 #` (kepekatan) dalam satu lembar: hasilnya **identik semua**, jadi Blueprint ECO80D mengabaikan kedua perintah itu — sama seperti mengabaikan bit Font B. Kartu "Ketajaman cetak", empat kolom `Setting`, `tuning.ts`, dan `buildSharpnessTestBytes` dihapus (migrasi `20260920140000_drop_print_tuning`). **Jangan menambahkan lagi pengaturan yang tidak berefek** — kalau huruf terlihat kurang tajam, penyebabnya ukuran huruf atau kertas, bukan pemanasan.
- **Preview layar adalah GRID KARAKTER selebar 48 kolom, bukan dokumen bergaya.** `PaperView` memakai lebar `48ch` (dari `RECEIPT_CHARS_PER_LINE`), satu baris layout = satu baris layar, dan **tidak ada baris yang punya ukuran huruf atau margin sendiri** — kalau ada, kolomnya tidak lagi sebaris dengan kertas. Dulu kotaknya 320px yang cuma muat ~37 kolom, jadi nama warung 47 kolom melipat di layar padahal tidak melipat di kertas; seluruh gunanya MockPrinter hilang kalau itu terjadi. Layar yang terlalu sempit **menggeser (scroll) overlay, bukan membungkus ulang struk**. Logo di preview dilebarkan `RECEIPT_LOGO_WIDTH_DOTS / FONT_A_COLUMN_DOTS` kolom supaya porsinya sama dengan di kertas.
- **Nama warung dibungkus otomatis, dan seimbang.** `wrapHeading` di `paper.ts`: kalau nama lebih panjang dari `RECEIPT_HEADING_WIDTH` (dua pertiga lebar kertas = 32 kolom) ia dipecah **di batas kata**, lalu dipakai lebar tersempit yang masih muat di jumlah baris itu — jadi blok tengahnya rata ("Mie Ayam Pangsit dan Bakso" / "Ciptarasa 4 Wonogiri", bukan "…Bakso Ciptarasa" / "4 Wonogiri"). Nama pendek tetap satu baris. Alamat dan telepon dibungkus keras di 48 kolom (`wrapWords`) supaya tidak pernah melewati tepi kertas. Semua dari `Setting`, **tidak ada yang di-hardcode** — ganti nama warung di Pengaturan dan pemecahannya ikut benar. Catatan: 48 tetap batas keras; nama 47 karakter sebenarnya MUAT satu baris, dipecah karena judul yang menempel di dua tepi kertas sulit dibaca.
- **Garis pemisah pakai karakter, bukan raster:** `=` antar BAGIAN besar, `-` di DALAM bagian, penutup `=============== Terima kasih! ===============` dengan teks di tengah. Garis raster 1-dot (versi opencode) nyaris tidak terlihat di kertas. Preview menampilkan dua baris `=` berturut-turut sebelum penutup — itu bawaan MockPrinter, diikuti persis.
- **Lebar = 48 kolom Font A, terukur di printer asli** (Tes Lebar Kolom, 20 Sep 2026): teks melipat tepat setelah 48 kolom, baris 48 penuh + LF tidak menambah baris kosong, penekanan ter-reset setelah judul/Total, dan tidak ada byte hilang lewat frame BLE 512 byte (24 baris bernomor cocok semua — tapi itu cuma ~2,5 KB; raster logo jauh lebih besar). 48 kolom memakai **seluruh lebar kertas 80mm — jangan dikurangi jadi margin.** Satu konstanta: `RECEIPT_CHARS_PER_LINE` di `paper.ts`. Bit font B di `ESC !` diabaikan printer ini (Font B tidak bisa dipilih lewat `ESC ! 1`); struk cuma memakai Font A. Foto struk lama yang memperlihatkan "harga bergeser satu baris" berasal dari versi kode sebelum `60d25c3` dan sudah tidak terjadi di layout sekarang.
- **Logo:** aset khusus thermal `public/assets/logo-ctr-thermal.png` — hanya mangkok + "CTR" tebal, **224 dot (≈28 mm)**, 1-bit, dibuat `scripts/make-thermal-logo.py` dari `reference/logo HD.png` (klasifikasi warna, bukan grayscale; teks melengkung dibuang). `logo-raster.ts` menggambarnya ke kanvas **pada ukuran asli tanpa scaling** — logo lama (260px, teks melengkung halus, di-scale) tercetak jadi bercak. Versi 416 dot (≈52 mm) memakan hampir seluruh lebar cetak, jadi dikecilkan ke 224 dot (raster ~14 KB/29 frame BLE → ~4 KB/9 frame). Toggle `Setting.printLogo` ("Cetak logo di struk"); preview layar ikut toggle yang sama.
- **Urutan bit raster: MSB = titik PALING KIRI** (`0x80 >> (x & 7)` di `logo-raster.ts`, bukan `1 << (x & 7)`). Ini penyebab sebenarnya logo rusak di kertas sampai 20 Sep 2026 — bukan dithering (PNG-nya murni hitam-putih, tidak ada abu-abu satu piksel pun) dan bukan frame BLE hilang. Mengepak terbalik **mencerminkan tiap kelompok 8 titik di tempatnya**, jadi bentuk keseluruhan tetap utuh — tidak bergeser, tidak terpotong, yang justru menyesatkan ke dugaan BLE — tapi tiap garis mendekati mendatar jadi bergerigi, tiap lengkung jadi coretan miring, dan huruf pecah jadi balok. 11,6% titik mendarat di kolom yang salah. Dibuktikan dengan mengepak dua arah lalu men-decode seperti printer (MSB dulu): hasil lama tidak sama dengan gambar sumber, hasil sekarang 0 titik beda, diperiksa lewat `buildLogoRaster` + `buildReceiptBytes` yang sungguhan sampai blok `GS v 0` di aliran byte. **Jangan naikkan `CHUNK_GAP_MS` untuk mengejar gejala ini** — 30 ms sudah terbukti cukup.
- **Driver cetak:** `Setting.printerDriver` = `webbluetooth` (default, terbukti mencetak di ECO80D lewat BLE) | `rawbt` (cadangan lewat app RawBT/Classic SPP; belum kita tes di kertas; dokumentasi RawBT: skema `rawbt:base64` mengirim data tanpa mengolah ulang) | `mock` (preview layar). Web Bluetooth: pairing sekali lewat tombol di Pengaturan (izin per-browser/per-tablet; tidak ada di iOS/Safari), tulis GATT dipecah ≤512 byte dengan jeda 30 ms (batas Chrome). Semua driver menerima byte yang sama dari `escpos.ts`; `Printer.printBytes` khusus diagnostik.
- **Cetak tidak pernah memblokir transaksi, tapi kegagalannya tidak boleh diam-diam:** kalau cetak otomatis saat Bayar gagal, layar Pembayaran tetap terbuka dengan "Struk belum tercetak" + penyebab dari driver + tombol "Coba Lagi"/"Lewati" (dulu cuma `console.error` lalu langsung pindah ke Order Aktif, jadi tidak ada yang tahu kenapa struk tidak keluar). Jalur "Ya, Cetak" juga tidak lagi pindah halaman saat gagal.
- **Alat diagnostik (Pengaturan, OWNER):** Tes Cetak (struk contoh dengan data warung asli dari `Setting`, tanpa baris "Kembali") dan Tes Lebar Kolom. `/print-preview` (konsol dev: preview + cetak ke driver terpilih) **OWNER only, dicek di server**.
- Potong kertas: struk tidak mengirim `GS V`; ada feed 5 baris di akhir untuk sobek manual. (Halaman produk Blueprint menyebut "Auto Cut = YES" sementara catatan lama bilang cutter manual — belum diuji.)

## Kertas dapur (kitchen ticket) — dibangun 22 Sep 2026

Tiket untuk dapur: dicetak di printer yang sama lalu disobek dan ditempel dekat kompor — beda tujuan dari struk (bukti bayar) dan daftar packing (checklist Antar sebelum bayar).

- **Toggle `Setting.kitchenTicketEnabled` ("Kertas dapur" di Pengaturan) — default MATI.** Mati = fitur ini tidak ada sama sekali, tidak ada pilihan yang muncul di mana pun (alurnya identik dengan sebelum fitur ini ada — sengaja, supaya hari pertama operasional 22 Sep 2026 tidak berubah). Nyala = kasir ditanya "Cetak kertas dapur?" Ya/Tidak setiap **simpan pesanan** dan setiap **tambah item ke order tersimpan** — **tidak pernah otomatis**, beda dari `autoPrintReceipt` struk (revisi keputusan pemilik: shift sepi vs ramai punya kebutuhan beda, jadi kasir selalu yang memutuskan). Tidak dicetak sama sekali saat **Pisahkan & Bayar** (item itu sudah dimasak). Pilih Tidak = pesanan tetap tersimpan normal seperti biasa.
- **Isi tiket satu sumber, sama seperti struk:** `buildKitchenTicketLayout` di `receipt-layout.ts` (dibaca `KitchenTicketView` untuk preview MockPrinter dan `buildKitchenTicketBytes` di `escpos.ts` untuk printer). Judul **"DAPUR"** (order baru) atau **"TAMBAHAN"** (item yang baru ditambah ke order tersimpan — **tidak pernah** mencetak ulang seluruh order, dapur akan masak dobel), lalu blok meta (Antrian, Tipe = channel+meja mis. "Dine In - L1"/"Bungkus", Nama kalau ada, Jam) — **keempatnya tebal**, tanpa header logo/nama warung sama sekali (tiket ini tidak pernah keluar warung). **HANYA item `isKitchenItem`** (Makanan + Minuman Racik, kolom yang sama dipakai timer Order Aktif) — Kulkas/Lain-lain/Frozen tidak dicetak sama sekali karena tinggal ambil. Item diurutkan dan dikelompokkan persis seperti keranjang (`sortOrderLines` + `layoutOrderLines`, ambang ≥5 porsi yang sama), add-on di bawah nama (nama saja, tanpa harga), **catatan dibuat menonjol** (`>> catatan <<`, tebal — satu-satunya baris item yang tebal). **Tanpa harga sama sekali di seluruh tiket.**
- **Pemicu cetak** (dua tempat, satu fungsi murni `buildKitchenTicketData` di `src/lib/orders/build-kitchen-ticket-data.ts`, dipanggil server-side dari action dan mengembalikan `null` kalau tidak ada satu pun baris `isKitchenItem` — caller lalu skip tawaran cetak sama sekali):
  - **Simpan pesanan** (`saveOrder`, `src/app/kasir/actions.ts`) — tiket "DAPUR" untuk SELURUH order baru.
  - **Tambah item ke order tersimpan** (`addItemsToOrder`, `src/app/order-aktif/actions.ts`, dipakai `AddItemsPanel` di detail order & layar Pembayaran) — tiket "TAMBAHAN" untuk item yang **baru saja ditambah di panggilan itu saja**, baik yang menjadi baris baru maupun yang menaikkan qty baris lama.
  - **Pre-order TIDAK otomatis** — tombol manual **"Cetak Tiket Dapur"** di detail order (`order-detail.tsx`, komponen yang sama dipakai detail order biasa DAN detail pre-order — lihat "Pre-order") untuk dicetak di hari pengiriman, plus dobel fungsi sebagai **tombol cetak ulang** untuk order biasa. Dibangun client-side langsung dari `order.items` (`OrderDetail` sudah membawanya sebagai prop), tanpa server action tambahan.
  - Prompt Ya/Tidak dipakai ulang lewat hook `useKitchenTicketPrompt` (`src/components/printing/use-kitchen-ticket-prompt.tsx`) di kedua pemicu otomatis.
- **Gagal cetak tidak pernah membatalkan/memblokir penyimpanan** — order/tambahan-item sudah tersimpan sebelum prompt muncul; gagal cetak cuma menampilkan penyebab + tombol "Coba Lagi"/"Lewati" (sama polanya dengan struk & bukti DP).
- `OrderItem.isKitchenItem` sudah ada dari Tahap awal (dipakai timer Order Aktif); `OrderDetailItem` (get-order-detail.ts) baru membawanya sejak fitur ini. `buildOrderItemsCreateData` sekarang mengembalikan `{ items, display }` — `items` persis seperti dulu (langsung ke `prisma.orderItem.create`, jangan pernah menambah properti ke situ karena Prisma menolak properti asing saat create), `display` adalah array paralel khusus untuk membangun cetakan (kitchen ticket), tidak pernah disimpan ke DB.

## Pembayaran

- **Satu tap langsung selesai**: kasir pilih metode — **Cash**, **QRIS**, atau **Cash + QRIS** (split, lihat di bawah) — lalu tap "Bayar". Tidak ada input nominal uang untuk Cash/QRIS biasa, tidak ada keyboard numerik di jalur itu.
- Tidak ada kalkulasi kembalian untuk order normal — `cashReceived` di server dianggap sama dengan total, dan struk tidak pernah mencetak baris "Kembali" (baris itu masih ada di layout HANYA supaya cetak ulang order lama yang punya `changeGiven` > 0 tetap akurat).
- Total selalu dihitung ulang di server saat pembayaran, tidak pernah percaya angka dari client.

### Split payment ("Cash + QRIS") — dibangun 22 Sep 2026

Kasus uang cash pelanggan kurang: sebagian dibayar tunai, sisanya QRIS, dalam SATU pembayaran (beda dari "Pisahkan & Bayar" di atas, yang memisah ITEM ke order baru — split payment tidak pernah membuat order baru).

- **Kasir cuma mengetik jumlah tunai** — porsi QRIS = total − tunai, dihitung dan ditampilkan otomatis, tidak pernah diketik. Preset tombol 10rb/20rb/50rb, tetap bisa diketik manual. Validasi (`validateSplitCashAmount`, `src/lib/orders/validate-split-payment.ts` — satu fungsi dipakai layar DAN server, CLAUDE.md "Total selalu dihitung ulang di server"): tunai harus > 0 dan < total; kalau tunai menyentuh total, sarankan pilih Cash; kalau tunai 0, sarankan QRIS.
- **Data:** `PaymentMethod.SPLIT` + `Order.splitCashAmount`/`splitQrisAmount` (keduanya `Int?`, diisi bersamaan hanya saat `paymentMethod === "SPLIT"`, jumlahnya selalu = yang benar-benar ditagih pembayaran ITU — total penuh biasanya, atau cuma sisa DP kalau pre-order ber-DP dilunasi lewat split). Migrasi `20260922180000_split_payment`, murni menambah (tidak mengubah baris/tabel lama).
- **BAGIAN PALING PENTING — rumus laci digeneralisasi, bukan ditulis ulang** (`src/lib/deposits/shift-math.ts`): `qrisPortionOf(order)` = total penuh untuk QRIS/TRANSFER, `splitQrisAmount` untuk SPLIT, 0 untuk CASH — lalu `cashSales = Σ(total − qrisPortionOf)`, `nonCashSales = Σ(qrisPortionOf)`. `isCashLike(method)` (CASH atau SPLIT) menentukan DP mana yang masuk `depositsAppliedCash` — DP yang menempel di order SPLIT ikut seluruhnya ke sisi cash (persis cara DP di order CASH biasa bekerja sebelum SPLIT ada), supaya "order dihitung sekali di Total Penjualan" (cash-portion + qris-portion = total, selalu) tetap benar tanpa pembagian pecahan DP. **Tanpa order SPLIT sama sekali, rumus ini byte-identical dengan rumus lama** — dibuktikan 22 Sep 2026 lewat 20.000 shift acak (69.572 order, campuran CASH/QRIS/TRANSFER + DP, tanpa SPLIT): nol selisih field dengan reimplementasi rumus lama. Enam skenario wajib (Full-Cash, Full-QRIS, Split, shift campuran, DP pre-order dilunasi via split, void order ber-split) semua diverifikasi aljabar-manual dengan selisih laci Rp0 — lihat riwayat kerja 22 Sep 2026 untuk angka persisnya. **Uji hidup di schema sementara (login sungguhan, klik UI) TIDAK dilakukan malam itu** — Prisma 7.10 punya pengaman yang menolak `prisma db push`/`migrate` kalau dipicu agen AI tanpa persetujuan real-time pemilik; pemilik menyetujui bukti aljabar sebagai cukup untuk push. Kalau suatu saat mengubah rumus ini lagi, ulangi uji aljabarnya dulu (`npx tsc`, `npx eslint src`, lalu proof).
- Void order yang dibayar SPLIT: porsi tunai harus keluar dari laci (dikembalikan ke pelanggan), porsi QRIS jadi pengembalian non-tunai — order yang di-void otomatis hilang dari `paidOrders` (`closeShift` cuma menjumlah status `PAID`), jadi tidak perlu case khusus di `shift-math.ts`.
- **Tampil di mana saja metode bayar lama tampil**: Riwayat Pesanan, detail order, badge "Sudah dibayar", notice Void, dan export Excel (2 kolom baru "Split - Cash"/"Split - QRIS") — semua lewat satu helper `formatPaymentMethodDetail`/`PAYMENT_METHOD_LABEL` (`src/lib/orders/payment-method-label.ts`), bukan ditulis ulang per layar. Struk: dua baris "Bayar (Cash)"/"Bayar (QRIS)" menggantikan satu baris "Bayar (...)" (`receipt-layout.ts`), termasuk saat sisa DP dilunasi via split.
- Tidak ada aksi baru khusus OWNER untuk fitur ini (`payOrder`/`payWithDeposits` tetap `requireUser()` biasa, sama seperti sebelum SPLIT ada) — jadi tidak ada capture-replay baru yang perlu diverifikasi untuk fitur ini secara spesifik.

## Order Aktif — timer

- Estimasi waktu masak = `prepBaseMinutes + prepMinutesPerPortion × porsi-yang-perlu-dimasak` (porsi dihitung dari kategori Makanan + Minuman Racik saja; Kulkas/Lain-lain/Frozen tidak dihitung karena tidak perlu prep).
- Oranye saat elapsed ≥ estimasi, merah saat elapsed ≥ 2× estimasi.
- `prepBaseMinutes` (default 4) dan `prepMinutesPerPortion` (default 1) disimpan di tabel `Setting`, harus bisa diubah dari halaman admin (belum dibangun — Tahap 11).
- Badge "Borongan" (order dengan total qty > 10) tetap tampil sebagai penanda visual, tapi warnanya sekarang ikut rumus di atas juga (tidak lagi otomatis netral/dikecualikan) — order borongan besar otomatis dapat toleransi waktu lebih lama karena porsinya lebih banyak.

## Pre-order

Order bisa dikasih tanggal+jam kirim (`Order.scheduledFor`). Sebelum hari H, order ini hidup di tab terpisah "Pesanan Terjadwal" (`/pesanan-terjadwal`), bukan Order Aktif — begitu `scheduledFor` terlewati, otomatis pindah ke Order Aktif seperti order biasa, tanpa langkah "aktivasi" apa pun (dua query di server cuma cermin satu sama lain dari cutoff waktu yang sama).

Dua aturan keras hasil diskusi dengan pemilik warung:

1. **Pre-order boleh dibuat TANPA shift terbuka.** Pesanan borongan biasanya masuk lewat WhatsApp malam hari saat warung sudah tutup — jadi pengecekan "harus ada shift terbuka" yang berlaku untuk order biasa (`saveOrder`) **tidak berlaku** untuk pembuatan pre-order (`savePreOrder`). Konsekuensi teknis: satu-satunya layar yang pasti bisa dibuka tanpa shift adalah `/shift/buka` (rantai redirect `/` → `/kasir` → `/shift/buka` memaksa lewat situ kalau belum ada shift), jadi link ke "Pesanan Terjadwal" wajib ada di layar itu juga, bukan cuma di Kasir/Order Aktif — kalau tidak, pre-order jadi tidak bisa dijangkau sama sekali malam hari.
2. **Pre-order TIDAK ter-attach ke shift yang kebetulan aktif saat dibuat.** `shiftId` dan `queueNumber` (keduanya nullable di skema, khusus untuk kasus ini) tetap `null` sampai pesanan itu **dibayar** — `payOrder` yang mengisi keduanya sekaligus, atomik, ke shift yang terbuka **saat pembayaran terjadi** (pola atomic-increment yang sama seperti `saveOrder`). Dengan begitu penjualannya selalu masuk ke shift hari pengiriman/pembayaran, bukan shift hari pemesanan (yang mungkin malah tidak ada shift sama sekali). Kalau pre-order jatuh tempo tapi belum dibayar dan tidak ada shift terbuka, `payOrder` menolak dengan pesan "Buka shift dulu sebelum membayar pre-order ini." — tidak mengubah data apa pun.

Konsekuensi dari aturan 2: pre-order yang belum dibayar **tidak boleh memblokir penutupan shift hari ini** — yang memblokir cuma order hari berjalan yang `shiftId`-nya sama dengan shift yang mau ditutup. Ini otomatis benar tanpa filter tambahan: `getUnpaidOrdersForShift(shiftId)` (dipakai `closeShift`) sudah query `where: { shiftId, status: "OPEN" }` sejak awal — pre-order yang `shiftId`-nya masih `null` otomatis tidak pernah masuk hitungan sampai dia benar-benar dibayar.

**Pengingat di layar Kasir.** Pre-order yang dicatat berhari-hari sebelumnya tidak pernah disebut lagi oleh mesin kasir sampai jatuh tempo — jadi layar Kasir punya bar merah yang muncul begitu ada pre-order yang jam kirimnya masuk jendela `Setting.preorderReminderMinutes` (default 120 = 2 jam, bisa diubah pemilik di Pengaturan: preset 30 menit / 1 / 2 / 3 / 6 jam, bukan isian angka — lihat "Konteks pengguna"). Bar-nya menyebut jumlah pesanan + jam kirimnya dan menuju `/pesanan-terjadwal` kalau ditap.
- **Tutupnya mengingat ID, bukan sekadar "bar mati".** `PreorderReminderBanner` menyimpan daftar id yang sudah ditutup di state komponen saja: refresh halaman memunculkannya lagi, dan pre-order LAIN yang masuk jendela memunculkannya lagi walau yang lama sudah ditutup. Tablet yang menyala semalaman tidak boleh bisa diam permanen soal pesanan yang harus dikirim.
- Semua jam diformat di **server** lewat `timezone.ts` lalu dioper sebagai string; komponen client cuma mencetaknya — jam tablet tidak pernah ikut menentukan arti "jam 18.30" (lihat "Zona waktu"). Jendelanya `(now, now + N menit]`, cermin dari `getUpcomingPreOrders`: yang sudah lewat `scheduledFor` sudah pindah sendiri ke Order Aktif. Pre-order `PAID` tetap dihitung — sudah dibayar bukan berarti sudah dimasak.
- Daftar pilihan ambangnya **satu sumber**, `src/lib/settings/preorder-reminder.ts` — dibaca kartu Pengaturan untuk merender tombol dan dibaca `updatePreorderReminderMinutes` untuk memvalidasi, jadi layar tidak bisa menawarkan nilai yang ditolak server.

Nama pemesan (`customerName`) **wajib** diisi khusus untuk pre-order (beda dari order biasa yang opsional) — sebelum dibayar, pre-order belum punya nomor antrian sama sekali, jadi nama adalah satu-satunya cara staf mengenali pesanan itu di layar.

### DP (uang muka) pre-order — dibangun 21 Sep 2026

Pesanan borongan sering dibayar sebagian di muka. Keputusan pemilik: **Opsi 1 — omzet diakui PENUH di hari kirim, DP hanya menggeser hitungan laci.** (Dua kalimat di permintaan awal — "DP bukan penjualan di hari DP" dan "yang dihitung penjualan hanya sisanya" — kalau diterapkan bersamaan membuat bagian DP tidak pernah jadi penjualan di hari mana pun, dan omzet Dashboard berselisih dengan Margin/Per Channel yang membaca `OrderItem` nilai penuh.)

- **Data: buku besar, bukan kolom.** Tabel `PreorderDeposit` (mengikuti pola `MieLedgerEntry`): tiap baris punya `kind` (`RECEIVED` DP diterima, `APPLIED` dipakai melunasi, `REFUNDED` dikembalikan, `FORFEITED` hangus), `method` (CASH/QRIS saja), `amount` selalu positif, `shiftId`, `createdById`. Sisa DP yang dipegang sebuah order = `RECEIVED` dikurangi semua yang menyelesaikannya; tidak pernah disimpan, tidak pernah diedit atau dihapus — koreksi = baris baru. Aritmetika murni ada di `src/lib/deposits/settle.ts` (`depositPosition`, `allocateDeposits`: DP tertua dipakai dulu, kelebihan dikembalikan dari DP terbaru dengan metode aslinya) dan dipakai layar, struk, server, dan uji sekaligus.
- **Rumus laci (satu fungsi murni: `computeShiftClosing`, `src/lib/deposits/shift-math.ts`):** `expectedCash = openingCash + cashCollected + depositsReceivedCash − depositRefundsCash − expenseTotal`, dengan `cashCollected = cashSales − depositsAppliedCash`. `cashSales`/`nonCashSales` tetap NILAI PENUH order yang dibayar hari itu (yang dibaca omzet/margin/per-channel); hanya laci yang tahu soal DP. DP tunai yang diterima hari ini ada di laci tapi bukan penjualan (`depositsReceivedCash`); DP yang diterima hari lain ada di dalam `cashSales` tapi tidak masuk laci hari ini (`depositsAppliedCash`, hanya dari order berbayar CASH — DP yang dipakai pada order QRIS tidak pernah ada di hitungan tunai). Tanpa DP semua suku DP = 0 dan hasilnya persis rumus lama.
- **Layar tutup shift menampilkan barisnya eksplisit** (di bagian "Hitungan Laci", hanya di hari yang ada DP-nya, jadi hari biasa tampil seperti dulu): "DP dipakai (sudah diterima sebelumnya)" −, "Penerimaan DP (tunai)" +, "DP dikembalikan (tunai)" −, dan di bawahnya yang tidak memengaruhi laci (penerimaan/pengembalian QRIS, DP hangus). Uang Seharusnya tetap disembunyikan sampai hitungan fisik dimasukkan.
- **DP tunai butuh shift terbuka; DP QRIS tidak** (uang tunai masuk laci, dan laci milik sebuah shift; QRIS tidak menyentuh laci, jadi tetap bisa dicatat malam hari lewat WhatsApp). Sama untuk pengembalian: tunai butuh shift terbuka, QRIS tidak. **DP hangus juga butuh shift terbuka** (ia diakui sebagai pendapatan pada hari pembatalan, dan hari itu diwakili shift).
- **Mencatat DP:** lewat "+ Catat DP" di detail pre-order yang masih `OPEN` (`recordDeposit`). **Bagian "Uang Muka (DP)" sudah dihapus dari keranjang Pre-order Baru** (21 Sep 2026, keranjangnya terlalu sempit) — layar itu selalu mengirim `deposit: null`. `savePreOrder` masih MENERIMA `deposit` (dibuat sekaligus dengan ordernya dalam satu statement, divalidasi sama) supaya jalurnya tetap utuh kalau suatu saat dipasang lagi, tapi tidak ada layar yang memakainya sekarang. Preset 50/100/200/500 rb + "Lain-lain" dan pil Cash/QRIS (tanpa keyboard di jalur utama). **DP melebihi total ditolak di server** dengan pesan yang menyebut total, DP sebelumnya, dan DP maksimal (`validateDeposit`, `src/lib/deposits/validate.ts` — satu-satunya pemeriksaan, dipakai kedua jalur). Pesanan yang sudah tertutup penuh oleh DP tidak menerima DP lagi. `recordDeposit`/`payOrder`/`cancelOrderWithDeposit` semuanya mulai dengan UPDATE kosong pada baris order (mengunci baris + memeriksa status) lalu MEMBACA ULANG item dan ledger di dalam transaksi, jadi dobel-tap Bayar, DP yang dicatat di perangkat lain, atau item yang dihapus sesaat sebelumnya tidak bisa membuat DP diselesaikan dua kali atau terhadap total yang basi.
- **Membayar order ber-DP:** `payOrder` menagih SISANYA saja (`payWithDeposits`, satu transaksi), menulis baris `APPLIED` (dan `REFUNDED` untuk kelebihan) dengan `shiftId` shift pembayaran. Layar Pembayaran menampilkan DP dan "Sisa dibayar", tombolnya "Bayar Sisa - Rp…"; kalau tidak ada yang perlu ditagih (DP menutup semuanya, atau order mengecil di bawah DP) tombol pilih metode hilang dan tombolnya "Selesai - Kembalikan Rp X" / "Selesai - Lunas oleh DP". **Order yang mengecil di bawah DP menampilkan "Kembalikan Rp X" — tidak pernah dianggap Rp0 diam-diam**, di Pesanan Terjadwal, detail order, Pembayaran, dan struk. Kelebihan itu keluar dari laci hari pembayaran kalau berasal dari DP tunai (`depositRefundsCash`). Order yang seluruhnya dibayar DP diberi `paymentMethod` = metode DP yang terbesar (label saja, tidak memengaruhi laci).
- **Pembatalan pre-order ber-DP** (`cancelOrderWithDeposit`, **OWNER only**, alasan wajib): dua pilihan. **"Kembalikan DP"** — dikembalikan dengan metode aslinya (tunai keluar dari laci hari itu, QRIS non-tunai). **"DP hangus"** — pelanggan batal, DP tidak dikembalikan, diakui pendapatan hari itu di kolom `forfeitedDeposits` (label "DP hangus"), terpisah dari penjualan makanan. Tombol batal biasa disembunyikan untuk order ber-DP (Order Aktif, detail order); kasir melihat penjelasan "hanya bisa oleh pemilik". Konfirmasi tidak aktif sebelum pemilik memilih nasib DP.
- **Yang ditolak server untuk order ber-DP** (bukan sekadar disembunyikan di layar): batal biasa (`cancelOrder`), **void order lunas yang memakai DP** (belum didukung — DP sudah diselesaikan ke shift yang mungkin sudah tutup, dan membatalkannya butuh langkah kembalikan/hanguskan sendiri supaya laci tetap jujur), Pisahkan & Bayar (DP milik seluruh order), dan Tandai Piutang.
- **Batasan yang diketahui:** (1) DP yang salah ketik tidak bisa dihapus — jalan keluarnya membatalkan pre-order dengan "Kembalikan DP" (efek bersih ke laci nol di shift yang sama). (2) Void order ber-DP ditolak (di atas). (3) Aktivitas yang terjadi di jendela milidetik antara `closeShift` membaca dan menulis (DP dicatat persis saat shift ditutup di perangkat lain) tidak dikunci — kelas balapan yang sama dengan order yang dibayar sambil tutup shift, dan tidak dipersempit di sini.
- **Cara pembuktiannya** (ulangi kalau mengubah rumus laci): skenario end-to-end dijalankan dengan fungsi server SUNGGUHAN (`openShift`, `savePreOrder`, `recordDeposit`, `payOrder`, `cancelOrderWithDeposit`, `closeShift`, …) di dalam proses terhadap **schema sementara `dp_test` di database yang sama** — dibuat dengan `prisma db push` memakai `DIRECT_URL` berakhiran `?schema=dp_test`, dan klien Prisma dibuat dengan `new PrismaPg({ connectionString }, { schema: "dp_test" })`. Ini aman HANYA karena kode aplikasi tidak memakai `$queryRaw`/`$executeRaw` sama sekali (SQL mentah tanpa nama schema akan menulis ke `public`) — jangan pernah menambahkannya tanpa memikirkan ini. Uang fisik di laci dihitung dari CERITA tiap hari (uang yang benar-benar berpindah), bukan dari rumus aplikasi, lalu `closeShift` dipanggil dengan hitungan itu: selisih harus 0. Hasil 21 Sep 2026: 179 pemeriksaan lulus — order biasa tanpa DP identik dengan rumus lama (dan uji properti 30.000 shift acak, ~224 ribu order, nol selisih), DP tunai Senin → lunas tunai Rabu, DP QRIS → lunas tunai (termasuk DP QRIS tanpa shift terbuka), DP tunai → lunas QRIS, DP dan kirim di hari yang sama, DP dua kali, batal "Kembalikan DP", batal "DP hangus", order mengecil di bawah DP, DP campuran tunai+QRIS, dobel-tap Bayar. Ditambah 36 pemeriksaan browser pada build produksi lokal, dan 4/4 shift tertutup NYATA dihitung ulang dengan rumus baru = angka beku. Setelah mengubah apa pun di sini: `npx tsc`, `npx eslint src`, dan ulangi skenarionya.
- **Catatan terpisah, bukan bagian DP:** pelunasan piutang (`RECEIVABLE`) lewat `payOrder` mempertahankan `shiftId` shift lamanya (yang sudah tutup), jadi uang tunai piutang yang dibayar belakangan tidak masuk hitungan shift mana pun dan bisa terbaca sebagai selisih lebih di hitung kas berikutnya. Ini sudah begitu sebelum DP; tidak diubah karena menyentuh arti angka beku.

## Shift & kas

- Transaksi diblokir kalau belum ada shift terbuka — kecuali pembuatan pre-order, lihat "Pre-order" di atas.
- **OWNER boleh membuka layar Kasir tanpa shift terbuka** (lihat menu/harga, siapkan keranjang) — layarnya menampilkan banner merah "Kasir belum dibuka" + tombol Buka Shift di paling atas, tombol Simpan Pesanan tetap terlihat tapi memunculkan popup "Shift belum dibuka" berisi tombol ke Buka Shift. **CASHIER tetap langsung di-redirect ke `/shift/buka`** (tidak ada yang bisa dikerjakan di sana sebelum shift ada). Ini murni soal layar mana yang boleh dilihat: `saveOrder` tetap menolak server-side ("Belum ada shift terbuka.") — sudah diverifikasi dengan menangkap request Simpan Pesanan asli lalu me-replay-nya setelah shift dihapus; server menolak, tidak ada order tercipta.
- `expectedCash` **tidak boleh** tampil ke kasir sebelum kasir input hitungan fisik uang (`countedCash`) — ini sengaja, supaya angka selisih (`difference`) tetap punya arti.
- **Layar hasil tutup shift = DUA bagian berjudul** (`ShiftSummary`, `src/components/shift/shift-summary.tsx`, permintaan pemilik 21 Sep 2026): **"Penjualan Hari Ini"** — Cash, QRIS (label "Non-Cash" sudah diganti; Transfer tidak ada lagi), Total penjualan = Cash + QRIS; lalu **"Hitungan Laci"** — Modal awal laci, Penjualan cash, Pengeluaran, baris DP (kalau ada), Uang seharusnya, Uang fisik dihitung, Selisih. Dipisah karena total penjualan memuat QRIS yang tidak pernah masuk laci; kalau bersebelahan dengan "Uang fisik dihitung", mata membandingkan keduanya dan mengira ada selisih. **Hitung-buta tetap**: komponen ini hanya dirender di langkah hasil, SETELAH hitungan fisik dimasukkan (diuji: sebelum itu tidak ada satu angka laci/penjualan pun di layar). Dashboard memakai komponen yang SAMA untuk rincian shift.
- Semua angka shift (`cashSales`, `nonCashSales`, `expenseTotal`, `expectedCash`, `countedCash`, `difference`) **dibekukan** saat tutup shift, tidak pernah dihitung ulang dari data live setelahnya (void minggu depan tidak boleh mengubah laporan shift yang sudah tutup). Sejak DP ada, enam kolom beku lain ikut dibekukan di saat yang sama (`depositsAppliedCash`, `depositsReceivedCash`, `depositsReceivedNonCash`, `depositRefundsCash`, `depositRefundsNonCash`, `forfeitedDeposits`) — `NULL` di semua shift yang tutup sebelum DP ada, dibaca sebagai 0, **tidak pernah dihitung ulang**.
- **Pengeluaran dicatat SEBELUM hitung uang fisik**, sebagai langkah eksplisit dalam alur tutup shift — bukan diandalkan dari input real-time selama shift jalan. Alasan: di lapangan pengeluaran biasanya dicatat di kertas dulu, baru diinput belakangan; kalau tidak dimasukkan sebelum hitung fisik, `expectedCash` salah dan selisih kas jadi alarm palsu tiap hari. Menu input pengeluaran harian (real-time) tetap ada sebagai opsi, tapi alur tutup shift punya langkah eksplisit "input pengeluaran dulu" sebelum "hitung uang fisik".
- Tutup shift diblokir kalau masih ada order berstatus `OPEN` (belum dibayar). Untuk tiap order yang belum selesai, kasir pilih salah satu:
  - **Batalkan** — untuk order salah input / tidak jadi. Sama persis dengan "Batalkan Order" di atas: status `CANCELLED`, boleh CASHIER, wajib alasan. (Dulu ini `VOID` khusus OWNER — diganti karena order belum dibayar tidak menyentuh uang; Void sekarang khusus order `PAID`.)
  - **Tandai Piutang** — order benar-benar belum dibayar pelanggan. Wajib isi nama (`customerName`). Status jadi `RECEIVABLE`, **tidak** dihitung sebagai penjualan cash/non-cash, dan muncul di halaman daftar piutang terpisah supaya bisa dilunasi belakangan.

Service worker (`public/sw.js`) **cuma cache shell aplikasi** — cache-first untuk build asset `/_next/static/*` (content-hashed, jadi cache tidak pernah basi), network-first untuk navigasi halaman dengan fallback ke `/offline` (halaman statis, HANYA saat benar-benar tidak ada koneksi). **JANGAN PERNAH** menambah antrian transaksi offline / background sync untuk menyimpan order saat offline — itu keputusan eksplisit, di luar scope Tahap 12 sepenuhnya.

Batasan penting yang sengaja dijaga:
- **Service worker tidak pernah cache atau menyajikan salinan basi dari halaman data-nya sendiri** (Order Aktif, Kasir, Dashboard) — cuma `/offline` yang di-precache, dan itu pun halaman statis tanpa data sama sekali. Alasan: nomor antrian atau kas yang basi lebih berbahaya daripada layar "tidak ada koneksi" yang jujur, untuk mesin kasir.
- `/offline` sengaja pakai **inline style, bukan class Tailwind/komponen `Card`/`Button` biasa** — `cache.addAll(["/offline"])` cuma nge-cache HTML halaman itu sendiri, bukan file CSS yang direferensikannya (nama filenya di-hash per build, tidak bisa ditebak dari `sw.js`). Kalau file CSS itu kebetulan belum pernah ke-cache lewat pola cache-first di atas, halaman offline yang pakai class Tailwind akan tampil sebagai teks polos tanpa gaya sama sekali — sudah dibuktikan (dan diperbaiki) secara langsung dengan mensimulasikan offline lewat Playwright.
- `src/proxy.ts` (auth gate) **wajib** mengecualikan `/manifest.webmanifest`, `/sw.js`, `/icon`, `/apple-icon`, dan semua file `.png` (ikon ada di `/icons/*.png`, `/icon.png`, `/apple-icon.png`; logo di `/assets/*.png`) dari matcher-nya — browser mengambil aset-aset ini lepas dari status login (bahkan dari halaman `/login` itu sendiri), dan registrasi service worker **gagal total** kalau responsnya redirect (bukan 200 asli) atau Content-Type-nya salah. `/offline` juga harus selalu bisa diakses langsung tanpa pernah di-redirect balik ke `/` walau user sedang login — beda dari `/login` yang memang harus redirect kalau sudah login.

Tombol **"Cetak Ulang"** di tiap baris riwayat pelanggan (`/note/frozen/pelanggan/[id]`), cetak langsung tanpa prompt (sama seperti cetak ulang struk di Riwayat Pesanan).
- **Printer Bluetooth cuma nyambung ke tablet Android — Safari iPhone sama sekali tidak punya Web Bluetooth.** Kalau `Setting.printerDriver === "webbluetooth"` dan `isWebBluetoothSupported()` (`web-bluetooth-printer.ts`) bilang tidak didukung, prompt Ya/Tidak dan tombol Cetak Ulang **tidak pernah menampilkan tombol yang pasti gagal** — ditukar penjelasan "cetak cuma bisa dari tablet kasir".
- **MIGRASI DATA — DIRENCANAKAN, BELUM DIJALANKAN (menunggu persetujuan pemilik).** Dicek 22 Sep 2026: **nol** baris `MieLedgerEntry` bertanda `productType = FROZEN` di produksi (percobaan semalam tidak sempat dipakai), dan **nol** order POS yang memuat produk "Mie Frozen" (produk itu ada & aktif tapi belum pernah benar-benar dipakai kasir). Yang ditemukan: satu pelanggan Mi Mentah bernama "rose KMK" dengan saldo awal Rp3.118.000 (dicatat 21 Sep 2026, SEHARI SEBELUM fitur Frozen apa pun ada) — belum jelas apakah ini utang Frozen yang salah tempat atau memang utang mi mentah biasa; pemilik perlu mengonfirmasi sebelum baris ini (kalau memang terkait Frozen) dipindah manual ke `FrozenCustomer`. Karena datanya nyaris kosong, tidak ada script migrasi otomatis yang ditulis — cukup butuh satu keputusan pemilik soal "rose KMK", lalu (kalau perlu) satu koreksi manual lewat UI.
- **MieProductType.FROZEN dipensiunkan, bukan dihapus** — Postgres tidak bisa `DROP` satu nilai enum tanpa menulis ulang kolom, jadi nilainya tetap ada di DB (baris lama yang masih bertanda begitu akan tetap ada sampai migrasi data di atas disetujui dan dijalankan), tapi tipe TypeScript `MieProductType` di `src/lib/mie/types.ts` sudah tidak menyertakannya — tidak ada jalur kode yang bisa menulis nilai itu lagi. Baris lama yang masih ada dirender pakai label `LEGACY_FROZEN_LABEL` ("Frozen (akan dipindah)") supaya tidak tampil kosong/undefined, dan `bucket-mie.ts`/Ringkasan Mi Mentah mengabaikannya sepenuhnya dari omzet/kg (balik ke "murni mi mentah" seperti sebelum percobaan semalam).
- **Deaktivasi produk "Mie Frozen" di Kasir BELUM dijalankan** — ini perubahan data produksi (`Product.isActive = false`), jadi menunggu persetujuan pemilik yang sama dengan migrasi di atas. Kodenya sudah siap: `getActiveMenu()` sekarang menyembunyikan kategori yang kehabisan produk aktif (`src/lib/menu/get-active-menu.ts`), jadi begitu produk itu dinonaktifkan lewat halaman Manajemen Menu yang sudah ada, tab kategori Frozen otomatis hilang dari Kasir tanpa kode tambahan.
- **Belum diverifikasi lewat capture-replay HTTP sungguhan** (beda dari pola CLAUDE.md "Server-side authorization" yang biasanya dibuktikan begitu) — tabel `FrozenCustomer`/`FrozenLedgerEntry` belum ada di database produksi (migrasinya menunggu persetujuan push yang sama), dan uji schema-sementara malam itu terblokir oleh pengaman `prisma db push` Prisma 7.10 terhadap agen AI tanpa persetujuan real-time. Diverifikasi lewat pembacaan kode saja: setiap fungsi `frozen-actions.ts` memanggil `requireRole("OWNER")` di baris pertama, pola identik dengan `note/actions.ts` yang sudah diverifikasi replay. **Lakukan capture-replay sungguhan begitu migrasi ini disetujui dan diterapkan ke produksi**, sebelum menganggap modul ini setara buktinya dengan Mi Mentah.

## Filter rentang tanggal

Tiga layar laporan punya rentang tanggal: **Riwayat Pesanan** (`/riwayat-pesanan`, lewat URL `?from=&to=`), **Ringkasan Mi Mentah** (`/note/ringkasan`), dan **Ringkasan Frozen** (`/note/frozen/ringkasan`) — dua yang terakhir murni client-side. Ketiganya memakai preset yang **persis sama** supaya pemilik belajar sekali: Hari ini / 7 hari / 30 hari / Bulan ini / Bulan lalu (`src/lib/date-range/presets.ts` + `DateRangePresets`). Preset langsung diterapkan (tidak perlu tap "Cari" lagi); isian dari–sampai manual di Riwayat Pesanan tetap butuh "Cari".

- **`today` selalu datang dari server** (`localDateStr`, Asia/Jakarta) dan dioper sebagai prop, tidak pernah dibaca dari jam perangkat — kalau tidak, tablet yang zona waktunya salah bisa menggeser arti "Hari ini". Matematika tanggalnya murni string `"YYYY-MM-DD"` (`Date.UTC` cuma dipakai sebagai kertas coretan hari, sama seperti `timezone.ts`).
- Batas hari di query tetap lewat `wibDateRange` (lihat "Zona waktu").
- **Batasan CASHIER "cuma hari berjalan" tidak bisa ditembus lewat preset atau URL**: `clampHistoryFilterForRole` di server memaksa `from=to=hari ini` untuk non-OWNER, dan preset/input tanggalnya memang tidak dirender untuk CASHIER (itu UX, bukan pengaman). Sudah diverifikasi: sesi CASHIER sungguhan membuka `?from=2020-01-01` hanya mendapat 10 order hari ini padahal ada 6 order lebih lama di database, sementara OWNER di URL yang sama mendapat semua 16.

## Server-side authorization

Setiap aksi khusus role OWNER **wajib** memanggil `requireRole("OWNER")` (dari `src/lib/auth/get-current-user.ts`) sebagai baris pertama di server action-nya sendiri — bukan cuma menyembunyikan tombol di UI. Menyembunyikan tombol itu UX, bukan keamanan; siapa pun bisa memicu server action lewat devtools tanpa lewat tombol sama sekali.

Sudah diverifikasi (bukan cuma dibaca kodenya): request asli ditangkap dari sesi OWNER yang klik "Batalkan", lalu direplay langsung ke server dari sesi CASHIER sungguhan (login beneran, request sungguhan, order id berbeda) — server menolak dengan HTTP 500 `"Forbidden: requires role OWNER"`, dan data di database tidak pernah berubah. Pola ini (`requireRole` di baris pertama action) wajib dipakai persis sama untuk setiap fitur OWNER-only berikutnya (dashboard, ubah harga, manajemen menu, manajemen user) begitu dibangun — dan diverifikasi dengan cara yang sama (capture request asli dari sesi berwenang, replay dari sesi tidak berwenang, cek server menolak DAN data tidak berubah), bukan cuma dicek lewat UI.

Diverifikasi ulang 20 Sep 2026 (build produksi lokal, sesi `owner` dan `kasir` sungguhan) untuk `updatePrinterDriver`, `updatePrintLogo`, dan `updatePrintTuning`: kontrol positif dari sesi OWNER (nilai = kondisi sekarang → `{"ok":true}`, membuktikan format request benar), lalu replay dari sesi CASHIER dengan nilai BERBEDA → HTTP 500, dan baris `Setting` identik sebelum/sesudah; nilai di luar rentang dari OWNER ditolak validasi server dengan pesan jelas. Halaman `/print-preview` juga OWNER only: kasir yang membukanya dialihkan ke `/kasir`.

Diverifikasi 21 Sep 2026 dengan cara yang sama untuk `updatePreorderReminderMinutes`: kontrol positif dari sesi OWNER (pilih "3 jam" → kolom benar-benar jadi 180 di DB, jadi format request-nya terbukti benar), lalu request itu di-replay dari sesi `kasir` sungguhan dengan nilai BERBEDA tapi tetap sah (360) → HTTP 500, dan `preorderReminderMinutes` tetap 180 sebelum/sesudah.

Diverifikasi 21 Sep 2026 untuk `cancelOrderWithDeposit` (aksi OWNER baru, `requireRole("OWNER")` di baris pertama): request asli ditangkap dari sesi OWNER yang menekan "Ya, Batalkan — DP Hangus" (kontrol positif: order jadi `CANCELLED` dan ledger mencatat `FORFEITED`), lalu di-replay dari sesi `kasir` sungguhan ke order LAIN yang juga ber-DP dan dengan pilihan berbeda (`REFUND`) → HTTP 500, order itu tetap `OPEN` dan ledger DP-nya tidak berubah. Aksi DP lain (`recordDeposit`, `getDepositReceipt`) memang boleh CASHIER (uang masuk, sama seperti membayar), jadi tidak OWNER-only.

## Design System

Semua layar wajib pakai token dan komponen terpusat ini — tidak ada lagi warna/radius/spacing pilihan sendiri per halaman.

**Token** (`src/app/globals.css`, via `@theme`): warna (`bg-canvas`, `bg-surface`, `text-ink` / `text-ink-muted` / `text-ink-faint`, `bg-primary` / `bg-primary-soft`, `bg-muted`, `bg-danger` / `bg-warning` / `bg-info` + varian `-soft`; bingkai foto produk: `border-photo-frame` dan `bg-photo-canvas`), radius (`rounded-pill`, `rounded-card`, `rounded-sheet`, `rounded-input`), shadow (`shadow-card`, `shadow-sheet`). Warna hijau (`--color-primary`) didekati dari referensi GoFood — bukan pixel-perfect (sumbernya foto WhatsApp), tapi searah.

**Tidak ada dark mode otomatis.** Ini kios di tablet tetap, bukan situs konsumen — tablet yang tiba-tiba ganti ke palet gelap yang belum pernah diuji di tengah shift lebih buruk daripada tidak pernah mendukung dark mode sama sekali.

**Komponen bersama** (`src/components/ui/`): `Button` (primary/secondary/ghost/danger — client, pakai `motion` untuk scale saat ditekan), `LinkButton` (tampilan identik `Button` tapi untuk navigasi `<Link>`, server-renderable, TIDAK boleh impor apa pun dari `button.tsx` karena itu file `"use client"` — style bersama ada di `button-styles.ts` yang netral), `Card` (permukaan putih di atas `bg-canvas`), `ListRow` (baris list dengan padding konsisten; pakai `onClick` untuk aksi in-page atau `asLink` untuk navigasi), `Sheet` (shell bottom sheet dengan drag handle), `Badge`, `PriceText` (lihat aturan hierarki di bawah).

**Aturan hierarki harga** (perbaikan dari `PriceText` weight prop) — dulu nama item dan harga sama-sama bold, sekarang:
- `weight="primary"`: harga produk sendiri di halaman custom/detail (subjek utama baris itu).
- `weight="secondary"`: harga di baris keranjang/order-item (nama item yang bold/subjek, harga jadi angka pendukung di sebelahnya), dan harga opsi add-on.
- `weight="total"`: SATU angka yang paling penting di layar itu (Total, Subtotal-sebagai-penutup-list, Selisih kas) — lebih besar, bold, dipisah garis pembatas dari baris-baris di atasnya. Subtotal/Total tidak boleh terlihat seperti baris item biasa.

**Satu aksi utama per layar/kartu.** Kalau ada dua tombol berdampingan, cuma satu yang `variant="primary"` (hijau solid, dominan) — sisanya `secondary`/`ghost`. Jangan biarkan dua tombol sama menonjolnya berebut perhatian.

**Animasi** (pakai `motion`, tidak ada properti yang memicu layout reflow, supaya ringan di tablet Android entry-level):
- **Sheet add-on Kasir ("Custom pembelian") sengaja TANPA animasi sama sekali** (`<Sheet animated={false}>`, tidak memakai `SheetItem`) — satu-satunya sheet yang begitu. Alasannya bukan selera: pembungkus stagger menyusutkan seluruh baris ke `scale 0.95` saat ditekan, dan di layar lebar itu menggeser tombol `+` selebar 48px sekitar 30px dari bawah kursor antara mousedown dan mouseup, jadi browser mengirim `click` ke barisnya, bukan ke tombolnya — stepper add-on tidak bisa dinaikkan sama sekali di laptop/tablet lebar (terbukti dan diperbaiki dengan tes klik di 1366px, 1180px, 390px, dan 844×390). Sheet ini dibuka puluhan kali per shift dan isinya banyak target kecil, jadi kecepatan dan ketepatan sentuh menang atas estetika. **Jangan kembalikan animasinya.** Sheet lain (Menu, popup konfirmasi, Pisahkan & Bayar, sheet Note) tetap beranimasi.
- **Sheet & popup lain** (permintaan pemilik — `Sheet`: Menu, popup konfirmasi Batalkan/Void, Pisahkan & Bayar, sheet Note): kontainer muncul dengan spring ~0.4s dari `y:-5, scale:0.95, blur(10px), opacity:0`; item di dalamnya muncul berurutan (`delay: index × 0.05`, dari `x:10, scale:0.95, blur`); item yang bisa di-tap punya hover (tint background, 0.4s) dan tap (scale 0.95, 0.2s). Semua di `src/components/ui/sheet-motion.tsx` (`sheetPanelMotion`, `SheetItem`, `HoverTint`) — pakai itu, jangan bikin variasi sendiri. **Pelajaran dari sheet add-on di atas: jangan pernah menaruh tombol kecil (stepper, ikon) di dalam `SheetItem interactive`** — pembungkus yang menyusut memindahkan tombolnya dari bawah kursor. Aman kalau seluruh baris itu sendiri yang jadi targetnya (Menu, daftar konfirmasi).
  - **Blur itu mahal di GPU** (pemilik sadar dan tetap mau): ada toggle **"Efek blur animasi"** di `/admin/settings` (`Setting.sheetBlurEnabled`, dibaca root layout tiap request lewat `getSheetBlurEnabled` → `SheetMotionProvider`) — kalau tersendat di tablet asli, pemilik mematikannya sendiri; gerak spring/stagger tetap ada, cuma blur yang hilang.
  - **`prefers-reduced-motion`**: tanpa blur dan tanpa gerak sama sekali, cuma fade 0.15s.
- Tekan tombol: scale ke 0.97-0.99, ~120ms (built-in di `Button`/`ListRow`/`ProductButton`).
- Item baru masuk keranjang: fade+scale singkat (~200ms), item lain di keranjang tidak ikut animasi.
- **Instan, tanpa animasi apa pun:** ganti kategori, tap tombol produk (aksinya, bukan feedback tekan), navigasi antar halaman.

**Header aplikasi — satu komponen untuk semua layar** (`AppHeader`, `src/components/ui/app-header.tsx`): tombol **Menu di kiri atas** (isi menu sama persis di mana pun — `MainMenu`, termasuk Kasir dan Order Aktif supaya dari Dashboard bisa langsung ke Note dll.), judul, aksi khusus halaman (Kembali/Batal pakai `size="compact"`, tetap 48px), lalu tombol Order Aktif paling kanan — satu bidang putih dengan satu garis bawah. Data header dari `getHeaderNav()` (indikator Order Aktif + `isOwner` untuk menyembunyikan entri OWNER — itu UX, bukan pengaman). Di HP label "Menu" disembunyikan (ikon saja) dan judul boleh 2 baris; judul yang tetap terlalu panjang di 390px dipendekkan (mis. "Harga Mi Mentah"). **Kasir** menyusun header sendiri dari potongan yang sama: tablet (≥1024px) satu baris Menu · channel/meja · Order Aktif; lebih sempit jadi dua baris terpisah (Menu + "Kasir" + Order Aktif, lalu baris channel selebar layar) supaya tombol channel tidak pernah tertimpa. **Pengecualian: jendela pendek (`max-height:500px`, yaitu HP landscape 844×390) balik ke satu baris** — di sana ruang vertikal yang langka, bukan lebar, jadi dua baris header malah memakan tab kategori. Halaman baru yang punya header wajib memakai `AppHeader`.

**Kasir — kategori & kartu produk:**
- Tab kategori **netral**: semua abu-abu muda (`bg-muted`) teks gelap, **hanya yang aktif hijau brand**; ikon kecil ikut warna teks. Tidak ada lagi warna per kategori (token `--color-cat-*` sudah dihapus).
- **Kartu produk bergambar**: gambar 4:3 di atas, nama, harga paling bawah; grid 2 kolom di HP, 3 kolom mulai ≥768px (dipakai juga oleh Pre-order dan Tambah Item — komponen yang sama). **Tinggi area gambar dibatasi `max-h-[140px]`** (dan 84px di jendela pendek, `max-height:500px` — HP landscape), karena rasio 4:3 tanpa batas atas bikin satu foto makan setengah layar di tablet 1366px. Lebarnya mengikuti kartu. Dengan batas ini 1180×820 dan 1366×1024 sama-sama muat 2 baris produk penuh.
  - **Foto dimuat UTUH (`object-contain`) di atas kanvas putih dengan bingkai 1px** (permintaan pemilik, 21 Sep 2026). Foto produk berlatar putih, jadi tanpa bingkai batasnya menyatu dengan kartu putih; dan `object-cover` memotong botol yang tinggi. Bingkai = token `--color-photo-frame` (abu-abu transparan, tipis), kanvas = token `--color-photo-canvas`. **Kalau suatu hari ada dark mode: definisikan ulang `--color-photo-frame` lebih terang, tapi biarkan `--color-photo-canvas` PUTIH** — file fotonya berlatar putih, kanvas gelap akan memunculkan batang putih di kiri-kanan foto.
  - **Kotak foto MASUK 6px dari tepi kartu, tidak menempel**, dengan sudut konsentris (radius kartu − 1px border − 6px inset = 9px, ditulis `rounded-[calc(var(--radius-card)-7px)]` di `product-button.tsx` — ubah bersama kalau inset/border kartu berubah). Menempel di tepi berarti bingkainya jatuh di atas garis tepi kartu dan terlihat sebagai satu garis tebal. Placeholder memakai inset dan sudut yang sama tapi TANPA bingkai (warnanya sendiri sudah menandai batas), supaya nama produk sebaris tetap sejajar. `ProductImage` juga dipakai thumbnail di Foto Produk, jadi ikut berbingkai.
  - Terukur 21 Sep 2026 (sebelum → sesudah): kapasitas grid Kasir 1366×1024 4,16 → 4,05 baris, 390×844 2,70 → 2,74, 844×390 1,11 → 1,07 (tinggi kartu +6px di tablet dan HP landscape, −3px di HP portrait karena lebar kotak foto menyempit). Layar Pre-order Baru di 844×390 sudah sempit dari dulu (baris tanggal + channel + tab memakan 252 dari 390px) — bukan akibat bingkai.
- Tanpa foto → **placeholder** (`ProductImage`, `src/components/ui/product-image.tsx`): blok warna lembut + inisial nama, warna diturunkan dari hash nama (sama di setiap render/perangkat). **Jangan pernah** memakai foto dari Google/stok — pemilik mengunggah fotonya sendiri.
- **Foto Produk** (`/admin/foto-produk`, OWNER, dijangkau dari halaman Pengaturan — bersama "Isi HPP"; dua-duanya diisi sekali lalu jarang disentuh, jadi sengaja TIDAK di Menu utama): unggah/ganti/hapus per produk. Browser memuat foto UTUH ke kanvas putih 800×600 (rasio 4:3, **tidak dipotong**; `resizeToCard`, `src/lib/images/resize-to-card.ts`) dan mengecilkannya ke WebP (~60-120 KB) sebelum kirim — PNG transparan ikut diratakan di atas putih. **Dulu foto dipotong-tengah ke 4:3 saat unggah dan hasil potongannya yang disimpan**: botol tinggi (1:3) tinggal ±25% bagian tengah, tutup dan dasarnya hilang selamanya, dan `object-fit` di kartu tidak bisa mengembalikannya. Diperbaiki 21 Sep 2026, sebelum ada satu pun foto terunggah (0 dari 25 produk) — jadi tidak ada foto lama yang perlu diunggah ulang; kalau suatu hari ada, foto yang diunggah sebelum tanggal itu tetap terpotong. Fungsinya diuji langsung di Chromium (21 pemeriksaan piksel: botol tinggi utuh, 4:3 identik dengan algoritma lama, lebar/kotak, PNG transparan). Action `uploadProductImage`/`removeProductImage` (`requireRole("OWNER")` baris pertama, diverifikasi replay dari sesi CASHIER — ditolak, data dan storage tidak berubah) menyimpan ke bucket Supabase Storage **`product-images`** (publik baca; tulis hanya OWNER lewat RLS `public.is_pos_owner()` — sesi kasir yang upload langsung ke bucket juga ditolak). Bucket + policy dibuat oleh migrasi `20260918090000_product_images_bucket`, jadi database production nanti ikut punya. Nama file baru tiap upload (URL berubah → tablet tidak menampilkan foto lama dari cache), file lama dihapus.

**Jebakan client/server yang sudah dua kali kejadian** — kalau bikin komponen UI baru yang punya varian client (butuh interaktivitas/motion) dan varian server-renderable (misal cuma `<Link>`), taruh logic/class yang dipakai bersama di file netral TANPA `"use client"`, jangan saling impor fungsi antar file client dan server. Lihat `button-styles.ts` sebagai contoh polanya.

**File `"use server"` CUMA boleh mengekspor fungsi async** — dan melanggarnya **lolos dari `next build`**. Kejadian 20 Sep 2026: `PREORDER_REMINDER_CHOICES` (sebuah array) diekspor dari `src/app/admin/settings/actions.ts`; `tsc`, `eslint`, dan `npm run build` semuanya bersih, tapi di runtime seluruh modul action itu gagal dimuat dengan `A "use server" file can only export async functions, found object` — dan kartu Pengaturan tetap menampilkan "Tersimpan ✓" padahal tidak ada yang tersimpan ke database. Taruh konstanta bersama di file netral (`src/lib/settings/preorder-reminder.ts`). **Pelajaran yang lebih besar: build yang hijau bukan bukti aksi server benar-benar jalan — cek nilainya di DB setelah menekan tombolnya.**
